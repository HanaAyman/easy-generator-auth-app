# AI Usage Disclosure

This project was built with [Claude Code](https://claude.com/claude-code) (Anthropic's
agentic CLI, running Claude) as an active pair programmer, not just autocomplete. Nearly
every file — backend and frontend — was generated by Claude inside an interactive session,
with me reviewing, redirecting, and correcting as it went. This document is my honest
account of that process: what worked, what I changed, and what I had to fix.

## What was AI-generated

Essentially all of it, on a first pass: the NestJS module/service/controller structure, the
Mongoose schema, the class-validator DTOs and password-policy regex, the Passport JWT
strategy, the exception filter and logging interceptor, the React pages and forms, the zod
validation schemas, the CSS Modules styling, the Jest/Vitest test suites, and this README.

What I did _not_ let it do on autopilot: pick the architecture. Every consequential decision
below was a checkpoint where I stopped it, made a call, and had it re-derive the plan or
code around that call — not the other way around.

## Decisions I made differently than the AI's default

- **Auth transport, twice.** Claude's first plan defaulted to a `Bearer` token returned in
  the response body (simplest to demo with Postman). I asked for the more secure option
  instead — an `httpOnly`/`Secure`/`SameSite` cookie the frontend never touches — and had it
  rework the `JwtStrategy`'s extractor, the controllers' cookie-setting logic, and the
  frontend's session model (checking `GET /users/me` on load instead of holding a token in
  state) to match. This is a case where the AI's first answer was the _faster_ build, not
  the _better_ one, and it only changed because I asked.
- **Folder structure.** Claude's default NestJS layout was feature-first (`auth/dto`,
  `users/dto`, etc.). I asked for a technical-role-first layout instead
  (`src/dtos`, `src/entities`, `src/services`, `src/controllers`, ...), which is how this
  repo is actually organized. Purely a style call, not a correctness one.

## Problems the AI ran into and how they got fixed

None of these were solved by "trying again with a better prompt" — they needed a human
reading the actual error and deciding what to do:

- **A completely full `C:` drive** caused `npm install` to fail with `ENOSPC` on the very
  first scaffold command. Claude diagnosed it via `df -h`, proposed redirecting npm's cache
  to `D:` via the global `.npmrc`, and — correctly — asked before touching a dotfile outside
  the project rather than just doing it.
- **A flaky-looking e2e suite that wasn't actually flaky.** The first e2e run appeared to
  hang, then failed every test with "Exceeded timeout of 5000ms for a hook." The real cause:
  Jest's default hook timeout (5s) is shorter than `mongodb-memory-server`'s first-run
  download-and-boot time for a real `mongod` binary. Fixed by raising `testTimeout` in
  `jest-e2e.json`, not by adding retries or weakening the assertions.
- **A self-contradicting test case I wrote.** One password-validation test case
  (`'nolettershere12345!'`) was labeled "missing a letter" but actually contained letters, so
  it correctly passed validation and failed my assertion. The regex under test was right; my
  test data was wrong. Caught by actually running the suite, not by inspection.
- **Docker crept back in by accident.** During manual verification, Claude spun up a local
  MongoDB container to test against, which quietly contradicted the earlier decision to use
  MongoDB Atlas (not Docker Compose) for this project. I called it out, and verification was
  redone using `mongodb-memory-server` in the automated e2e suite instead — no Docker
  dependency anywhere in the delivered stack.
- **Two security-relevant misses caught in review, not by the AI itself.** The global
  exception filter fell back to `exception.message` for _any_ `Error`, not just ones we threw
  on purpose — so an unhandled Mongo driver error or `TypeError` would have leaked internal
  detail (DB errors, file paths) straight to the client on a 500. Separately, `UsersController`
  was decorated with `@ApiBearerAuth()` for Swagger even though the API never uses a bearer
  token — auth is a cookie. So used the decorator for `@ApiCookieAuth('access_token')` instead.
  Neither was caught by tests or lint — both needed someone to read the code with an
  eye for what it actually does versus what it's supposed to do.

## What worked well

- Describing the target architecture in plain constraints ("cookie-based session, not
  Bearer," "technical-role folders, not feature folders") and letting Claude re-derive the
  concrete file layout from that was far faster than specifying files by hand.
- Using the AI to write the _first_ draft of the Jest/Vitest suites, then reading the actual
  failures to find real bugs (the test-timeout issue and the bad password fixture above) —
  the tests earned their keep by failing correctly, not by passing on the first try.
- Asking it to run lint/build/test after every meaningful change caught type and style
  issues immediately instead of accumulating them.
